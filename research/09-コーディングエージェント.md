# 09 コーディングエージェント

モダンな開発手法が定着していない部門でも、コーディングエージェントを入れると開発は何が変わるのか。
この記事はその変化と、前提となる開発統制を扱う。一般エージェントの統制は
[08](08-IT部門向けAIエージェント.md)に譲る。

一般的なチャット型AIと違い、コーディングエージェントはファイルの読み書きやコマンド実行を伴う。
だからこそ統制が要るが、全部揃えてから始める必要はない。バージョン管理・コードレビュー・機密
ファイルの除外設定・本番と切り離した実行環境の4つは初日から整え、テストとシークレットスキャンは
利用範囲を広げるタイミングで追加すればよい（3節）。

> 一般AI導入とは別の**パイロットトラック**として扱う。文章・調査用途のパイロットとは対象者・
> 前提条件が異なるため、[10](10-パイロット運営.md) で個別に計画する。

## 1. 前提：この部門の現状

想定する小規模IT部門は、簡易な開発（簡易ツール・スクリプト作成等）は行っているものの、
バージョン管理（Git）・コードレビュー・自動テスト・CI（継続的インテグレーション）といった
**モダンな開発手法が定着していない**ことが多い。属人化した「動けばよい」スクリプトが、
担当者しか把握していない状態で本番運用されているケースも珍しくない。

## 2. 何が変わるか・何ができるようになるか

- **内製化の範囲が広がる**: これまで「外注するほどでもないが自分で書く時間もない」という理由で
  見送られていた小規模開発・自動化が、内製で対応しやすくなる。
- **属人運用のコード化・再現性向上**: 担当者の頭の中にしかなかった手順が、コードとドキュメントとして
  残りやすくなる（コーディングエージェントは説明・ドキュメント生成も得意）。
- **モダンな開発手法への移行の敷居が下がる**: コードレビューやテストコードの作成自体を
  エージェントに補助させることで、「導入したいが手が回らない」だった改善に着手しやすくなる。

これらは「開発者がいなくても開発できる」という意味ではなく、**開発の初速・下書きの質が上がる**
という意味である。最終的な正しさの確認・意思決定は引き続き人が担う（[01](01-導入判断.md)2.2節）。

Google CloudのDORAが2025年に公表した調査でも、AIコーディングアシスタントの導入で開発者の
80%以上が生産性向上を、59%がコード品質への好影響を報告した一方、組織全体の成果は
「AIは既存の開発体制を映す鏡であり増幅器」という結果になっている
（[Google — How are developers using AI? Inside Google's 2025 DORA report][ref-dora-2025]、
2025-09-23付、確認日: 2026-07-14）。バージョン管理やレビュー体制が弱い組織では、AIがその弱さ
ごと増幅してしまう。3節の統制を初日から外さない理由はここにある。

## 3. 導入前提となる開発統制

コーディングエージェントは、一般的なチャット型AIと異なり、**ファイルの読み書き・コマンド実行**を
伴う場合がある。統制は一括で完成させてから始めるのではなく、**利用範囲に応じて段階的に整備する**。
最低限（3.1節のバージョン管理・コードレビュー・依存関係の確認、3.2節の機密ファイル除外設定、
3.4節の実行環境分離）は初日から必須とし、テスト・シークレットスキャン（3.1・3.3節）は、本番反映や
書き込み権限の付与など利用範囲を広げるタイミングに合わせて追加する。

以下はClaude Codeの設定を例に説明するが、Codex（OpenAI）等の同種製品にも同じ考え方が当てはまる。
Codex CLIにも、ファイル単位でアクセスを拒否する`deny`ルールを持つパーミッションプロファイルがある。
**ただし2026-07時点でこの機能はBeta（「開発が進行中で変更されうる」）であり、旧来の`sandbox_mode`
（および`sandbox_workspace_write`）設定と併用できない**。設定ファイルに`sandbox_mode`が
存在する、`--sandbox`を指定する、または選択中の設定プロファイルが`sandbox_mode`を設定している
場合は、`default_permissions`によるパーミッションプロファイルではなく旧来のsandbox設定が
優先される（[OpenAI — Codex: Permissions][ref-openai-codex-permissions]、確認日: 2026-07-14）。
機密ファイル除外をパーミッションプロファイルで設定したつもりでも、旧`sandbox_mode`設定が
残っていると無視されるため、**導入時に自社の設定ファイルに`sandbox_mode`が残っていないかを
確認し、`default_permissions`/`[permissions]`側の設定が実際に有効になっているか管理画面・
実行結果で動作確認する**。個別の設定方法は、使う製品の公式ドキュメントを確認する。

### 3.1 基本の開発統制

- **バージョン管理（Git）**: 変更履歴を残し、意図しない上書き・喪失を防ぐ。
- **コードレビュー**: エージェントが生成したコードも、人によるレビューを必須にする
  （[01](01-導入判断.md)2.2節の「精度懸念は運用で管理する」の実践）。
- **テスト**: 最低限の動作確認（手動でも可）を、本番反映前のルールとして定める。
- **依存関係の確認**: 追加されたライブラリ・パッケージの出所・ライセンスを確認する。

### 3.2 機密情報の除外設定

**「`.claudeignore`で機密ディレクトリを自動除外できる」という理解は誤り**であり、Claude Codeに
そのような公式機能は存在しない（2026-07-14時点で確認）。機密ファイル・ディレクトリの除外は、
`settings.json` の `permissions.deny` にファイル読み取りの拒否パターンを明記する方式が正式である
（例: `"deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]`、
[Claude Code Docs「Settings」][ref-claudecode-settings]、確認日: 2026-07-14）。

ただし、Bashコマンド経由で間接的にファイル内容へアクセスできる可能性が理論上あるため、
**権限設定だけに頼らず、サンドボックス化・実行環境分離と併用する**（[05](05-セキュリティ法務調達.md)5節）。

### 3.3 データ送信に関わる設定

- **`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` 環境変数**: 設定すると、テレメトリ・Sentryへの
  エラーレポート・`/feedback`・セッション品質アンケートなど、非必須の通信をまとめて止められる
  （[Claude Code Docs「Environment variables」][ref-claudecode-envvars]、確認日: 2026-07-14）。
- **`/feedback` コマンドの扱い**: 実行すると、その時点の会話履歴（コードを含む）がAnthropicに
  送信され、5年間保持される。社内では原則禁止とし、必要な場合のみ個別許可する運用が無難
  （[Claude Code Docs「Data usage」][ref-claudecode-datausage]、確認日: 2026-07-14）。
- **リポジトリ側のシークレットスキャン**: APIキー・認証情報の混入を、コード側でも検知する仕組みを
  併用する。

### 3.4 実行環境の分離

エージェントにコマンド実行権限を与える場合、本番環境と切り離した開発・検証環境で運用する。
特に、社内システムへの書き込み・設定変更を伴う自動化は、人によるHITL承認を挟む
（[08](08-IT部門向けAIエージェント.md)4.3節と同じ考え方）。

## 検討のポイント

- 一般AI導入（文章・調査用途）のパイロットと並行し、コーディングエージェントは**別トラック**として、
  対象者（実際にスクリプト作成を行うメンバー）を絞って開始する。
- 導入前に、最低限のGit運用・コードレビュー体制・機密ファイルの除外設定（3.2節）・本番と切り離した
  実行環境（3.4節）を整える。テスト・秘密情報検知は、対象範囲を本番系や書き込み権限に広げるタイミングに
  合わせて段階的に整える。
- `/feedback`の利用可否、シークレットスキャンの導入は、開発統制チェックリストの必須項目にする。
- Codexのパーミッションプロファイル（`deny`設定）を使う場合は、Beta機能である旨と、旧来の
  `sandbox_mode`設定が残っていると無視される仕様（3.2節）を踏まえ、設定後に実際の動作を確認する。
