# 08 IT部門向けAIエージェント

他部署にAIエージェントの活用を提案するには、まず自分たちが本格的に使った経験が要る。エージェントは
コネクタ経由の横断参照・要約・複数手順の自動実行で、IT部門業務（問い合わせ対応・棚卸し・
ドキュメント整備・小規模開発）を効率化できる。ただし効果も安全性も、情報基盤・権限設計・評価の
仕組みが伴って初めて出る。

エージェント固有のリスクは**権限越境**（アクセス権はあるが本来その用途では見ない情報が、横断的に
読まれ別文脈に再出力されるリスク）だ。従来のSaaS・ストレージにはなかった論点で、コネクタ許可制と
最小権限設計が対策の柱になる。統制の役割分担・承認フローの正本は[04](04-ガバナンス.md)、一般的な
情報分類は[05](05-セキュリティ法務調達.md)に譲り、この記事はエージェント固有の論点（何ができるか・
どこが限界か・権限越境をどう抑えるか）に絞る。

## 1. なぜ小規模IT部門自身が本格的に使う必要があるか

小規模IT部門が他部署にAIエージェントの活用を提案・設計し、そのリスクを評価する立場に立つには、
まず自分たちが本格的に使った経験を持っている必要がある（[00](00-概要.md)3節）。

### 1.1 「使っていない部署は提案できない」

- コネクタ許可制・権限設計・監査ログ・エージェントの多手順自律実行といった、実際の統制設計で
  問題になる論点（4節）は、触ってみて初めて実感を持って理解できる。資料やベンダーの説明を
  読むだけでは、「どこで権限越境が起きうるか」「どのコネクタが業務に必要か」といった勘所が
  つかめない。
- **本プロジェクトの見解**: 自ら使わずに他部署へ導入を提案・設計すると、リスクの見落としと
  過剰な制約の両方が起きやすい（リスクの実感がないまま「念のため禁止」に倒れるか、逆に
  実際には危険な使い方を許可してしまうかのどちらか）。小規模IT部門限定パイロット（[11](11-段階導入ロードマップ.md)
  1節）は、この経験を積むための第一段階として位置づけられる。

### 1.2 簡易的なAIサービスで得られる知見の限界

自部門で「何らかの形でAIを使っている」ことと、「エージェント活用を他部署に提案・設計できる状態」
の間には、利用形態によって大きな差がある。

- **簡易的なAIサービス**（API経由の簡易チャットボット、社内ポータルに埋め込んだチャットボット、
  素のAPI呼び出しだけを使う自作ツール等）は、コネクタ・ツール呼び出し許可制・監査ログ・
  権限設計・多手順の自律実行（[用語集](../docs/glossary.md)「AIエージェント」）といった、
  エージェント固有の統制論点（4節）に触れる機会がない。単発の質問応答にとどまるため、
  得られる知見も「文章の精度」程度にとどまりやすい。
- 一方、**法人プランの正規UI・エージェント機能を直接使う経験**（Claude/ChatGPT等の管理者コンソール、
  コネクタ設定、権限越境が実際に起きかけた事例等）は、4節で扱う固有リスクを自分ごととして
  理解する材料になる。
- **本プロジェクトの見解**: 簡易的なAIサービスの利用実績だけで「AIを使っている」と評価し、
  エージェント導入の意思決定・提案を進めるのは早計である。小規模IT部門限定パイロットの対象は、
  文章作成等の汎用チャット利用にとどめず、コネクタ・エージェント機能を含む正規の法人プラン
  （[06](06-製品プラン比較.md)）とすることが望ましい。

## 2. 何ができるようになるか

AIエージェントは、単発の質問応答（チャット）と異なり、目標に対して**複数のツール・コネクタを
使いながら自律的に複数手順を実行**できる（[用語集](../docs/glossary.md)「AIエージェント」参照）。
IT部門業務での適用例は以下の通り。

- **問い合わせ対応**: ナレッジベース・過去のチケット履歴を横断参照し、一次回答案を作成する。
- **棚卸し・調査**: 複数システム（資産管理台帳、契約管理システム等）から情報を集約し、
  差分・不整合を洗い出す。
- **ドキュメント整備**: 散在する手順書・設定情報を要約・構造化する。
- **小規模開発・自動化**: 定型的なスクリプト作成、設定変更の下書き（コーディングエージェントの
  詳細は [09](09-コーディングエージェント.md)）。

いずれも小規模IT部門自身の業務範囲であれば、大きな新規投資や外部連携の拡張なしに今日から
着手できる。ここで得た経験は、そのまま他部署への展開時の具体的な提案材料になる
（[03](03-効果とDX.md)4節）。

## 3. どこまで行けるか・限界

エージェントの効果と安全性は、次が伴わないと頭打ちになる。

- **情報基盤の整備**（[03](03-効果とDX.md)3節）: 参照先のナレッジが整理されていないと、
  エージェントは的外れな回答をするか、古い情報を参照し続ける。
- **権限設計**（4節）: 誰の権限でどのシステムにアクセスするかが曖昧だと、範囲を広げるほど
  リスクが増える。
- **評価の仕組み**: 出力の正しさをどう検証するか（人によるレビュー、テストケースでの評価）を
  用意しないと、間違った自動実行に気づけない。

小規模IT部門限定パイロットの段階では、**IT部門自身の業務に閉じた範囲**でエージェントを使う。
ただし、範囲を閉じること自体が権限越境対策になるわけではない（4節参照、対策の本丸は権限設計
そのもの）。コネクタ許可制・最小権限設計（4.1節）を運用しながら固めていく段階では、対象システムを
絞ったほうが審査・検証の手間を管理しやすい、というのが理由だ。他部署のシステムへの横断アクセスは、
権限設計・審査の運用が固まってから慎重に拡大を検討する。

## 4. 固有リスクと統制

### 4.1 権限越境（本プロジェクトでの用語）

従来のSaaS・ファイルストレージでは、人がアクセス権の範囲内で個別にファイルを開く、という
利用形態だった。エージェントでは、**コネクタ経由でその人の権限のもと、横断的に情報を読み、
要約して別の文脈に出力する**という利用形態になる。

その結果、「アクセス権としては持っているが、本来その用途・その会話では見るべきでない情報」が、
意図せず結合・再出力されるリスクが生じる。これは**従来のSaaS・ストレージには無かった論点**であり、
エージェント固有のリスクとして特別に扱う必要がある。

ただし、「IT部門自身の業務に閉じている（2節）から安全」と単純化してはならない。IT部門はID管理・
全社資産台帳・契約情報・管理者権限など、**組織の境界を越えて全社に影響しうる情報・権限**を
扱う立場にあり、対象業務がIT部門内であることは越境リスクの限定にはならない。実際に影響範囲を
限定するのは、エージェント専用アカウント・読み取り専用権限・検証環境での実行・接続先データの
個別審査（本節「対策の本丸」参照）であり、組織範囲ではなく**権限設計そのもの**である。とはいえ、
この段階のパイロットは対象業務・データの種類が絞られている。権限越境の実例を安全に洗い出し、
全社展開の前に対策を固める機会として使える（[10](10-パイロット運営.md) 測定指標3、
[11](11-段階導入ロードマップ.md) の判断材料）。

対策の本丸は次の2つ。

- **コネクタ許可制**: どのシステムへの接続を許可するかを、管理者が個別に審査・承認する
  （[05](05-セキュリティ法務調達.md)4節）。ツール呼び出し単位で「常に許可／要承認／ブロック」の
  粒度で制御できる製品もある（[05](05-セキュリティ法務調達.md)4節）。
- **最小権限・職務分離・読み取り/書き込み分離**: エージェント専用のアカウント・権限セットを用意し、
  個人の全権限をそのまま使わせない。書き込み・実行系の操作は特に慎重に権限を絞る。

### 4.2 その他の固有リスク

- **プロンプトインジェクション**（[用語集](../docs/glossary.md)参照）: 参照先データ（Webページ、
  外部ドキュメント等）に紛れ込んだ指示によって、エージェントが意図しない動作をする攻撃。
  外部データを参照するコネクタほど注意が必要。
- **間接的な機密取得**: 直接的な入力禁止（[01](01-導入判断.md)）だけでなく、コネクタ経由で
  間接的に機密情報へアクセスしてしまう経路がないかを確認する。
- **外部ツールのサプライチェーンリスク**: サードパーティ製のコネクタ・MCPサーバーを利用する場合、
  その提供元の信頼性・セキュリティも審査対象にする。

### 4.3 運用対策

- **HITL（Human-in-the-loop）**: 重要な操作（書き込み・送信・削除等）はAIだけで完結させず、
  人の承認・確認を挟む。
- **出力評価・根拠確認**: エージェントの出力について、根拠となった参照元を確認できるようにする。
- **権限越境テスト・コネクタ審査**: 新しいコネクタを有効化する前に、意図しない情報への
  アクセス経路がないかをテストする。

## 5. エージェントの種類とハイブリッドな効率化

4節までは、エージェントを安全に使うための統制を扱った。ここからは、2節・3節で見た
「何ができるか・どこまで行けるか」を、実際にどう積み上げて効率化していくかを扱う。エージェントの
種類を区別し、スクリプト・スキル・スケジュールを組み合わせるハイブリッドな進め方をとると
効率化しやすい。

### 5.1 エージェントの種類

**本プロジェクトの整理**として、エージェントを**ローカル操作エージェント（コンピュータ操作型）**と
**ワークフロー型エージェント（オーケストレーション型）**という2つの類型で捉えると設計しやすい（定義は
[用語集](../docs/glossary.md)「エージェント関連」を参照）。ただし、互いに排他的な製品カテゴリでは
ない。1つのエージェントが両方の性質を併せ持つこともある、理解のための整理だ。

Microsoft Copilot Studioの公式ブログは、UI操作を伴うエージェント（本記事のローカル操作エージェントに
近い）と、API起点の構造化されたワークフローを区別している。そのうえで「組織は複数段階の
ワークフローの中に、UI自動化に対応したエージェントを直接組み込める」とし、決定的な処理は
ワークフローが、推論を要する複雑な判断はエージェントが担当する**組み合わせ**を、業界の方向性として
示している（[Microsoft Copilot Studio Blog][ref-ms-copilotstudio]、2026-05付、確認日: 2026-07-13）。
ただし同ブログは、両者を厳密に排他的な2分類として提示しているわけではなく、組み合わせ方の一例として
参照している。

**本プロジェクトの見解**: 小規模IT部門でエージェント活用を進める際も、「何でもエージェントに任せる」
のではなく、決定的な手順はワークフロー（またはスクリプト、5.2節）に、判断が要る部分だけをエージェントに
任せる設計が、再現性・ガバナンスの効かせやすさの両面で有効である。

### 5.2 スクリプト・スキル・スケジュールを積み上げるハイブリッド型の効率化

1節で述べた「本格的に使う経験」を積む中では、次のように段階的に積み上げていくと効率化しやすい。

1. 最初は都度のチャット・エージェント利用から始める。
2. うまくいったやり取り・手順を、再利用可能な「スキル」として型化する。Anthropicは、指示・スクリプト・
   参考資料をフォルダにまとめ、エージェントが必要に応じて段階的に読み込む仕組み（Agent Skills）を
   提供しており、汎用エージェントを特定業務に特化させる方法として説明している
   （[Anthropic「Equipping agents for the real world with Agent Skills」][ref-anthropic-skills]、
   2025-10-16付、確認日: 2026-07-13）。
3. 定型的に繰り返す作業は、スケジュール実行に載せる。Claude Code Routinesのように、決まったプロンプト・
   接続先・実行環境をまとめて保存し、定期的なスケジュール・APIコール・特定イベント（例:
   リポジトリの更新）をきっかけに自動実行できる仕組みがある。ただしRoutinesは2026年7月時点で
   リサーチプレビュー（research preview）段階の機能であり、対象プラン・トリガー種別・実行環境の
   仕様は変更される可能性がある
   （[Anthropic「Automate work with routines」][ref-anthropic-routines]、確認日: 2026-07-13）。
4. 決定的な処理（フォーマット変換、定型的なデータ加工等）はスクリプトに任せ、エージェントの自律判断は
   本当に判断が必要な箇所に絞る。

**本プロジェクトの見解**: この積み上げ方（都度利用 → スキル化 → スケジュール化 → スクリプトとの
併用）は、小規模IT部門が1節で述べた「本格的に使う経験」を、場当たり的な利用で終わらせず、再現性の
ある資産として蓄積していくための実務上の勘所である。パイロットの初期から意識しておくとよい。

### 5.3 設計・改善にAIを使う（自己レビュー・自己改善サイクル）

エージェントやスキルの設計そのものを、AIと一緒に考えることも有効である。設計案をAIにレビューさせ、
運用開始後も定期的に振り返り・改善するサイクルを回すことで、属人的な試行錯誤に頼らず改善速度を
上げられる。これは、[03](03-効果とDX.md)4節で触れている「本資料の作成・レビュー自体もAIを使って
行っている」という本プロジェクトの実践と同じ考え方だ。詳細は03を参照し、ここでは繰り返さない。

## 検討のポイント

- パイロット初期は、IT部門自身の業務（自部門のナレッジベース・チケット管理等）に閉じた
  コネクタ構成から始め、他部署システムへの接続は慎重に段階を踏む。
- 新しいコネクタを追加するたびに、コネクタ審査チェックリストで確認する運用を最初から組み込む。
- 権限越境の実例（危なかった箇所）は、[10](10-パイロット運営.md) の測定指標3として記録し、
  [11](11-段階導入ロードマップ.md) の定期見直し（Go/Hold/Stop判断）の判断材料にする。
