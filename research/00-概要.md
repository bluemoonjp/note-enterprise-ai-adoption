# 00 概要（読み方・前提・原則）

この資料は、非IT中小企業（100〜500人規模）の小規模IT部門が、自社でAI・AIエージェントを
導入する際にどう考え、どう進めるかを整理した解説資料である。本記事（00）は各論には立ち入らず、
この先を読み進める前に共有しておきたい前提・原則と読み方の地図を示す。各論の結論・根拠は
[01](01-導入判断.md)以降の各記事に譲り、記事ごとの想定読者・扱う論点は
[記事インデックス](README.md)を参照する。

## この資料の前提・読み方

- **想定する進め方**: 全社一斉導入ではなく、小規模IT部門がまず自部門にAI・AIエージェントを
  導入し、そこで得た知見をもとに次の展開を判断する（[01](01-導入判断.md)、
  [11](11-段階導入ロードマップ.md)）。
- **導入するプランと対象**: Claude Team等の法人プランを想定し、対象は文章・調査・整形・コード
  など汎用作業から始める。個人情報・機密データを扱う業務は対象外とする（[01](01-導入判断.md)、
  [05](05-セキュリティ法務調達.md)）。
- **統制の骨格**: 情報区分に基づく入力可否ルールとマスキング運用、コネクタ許可制・最小権限設計、
  測定指標を先に決めてから始めるという3つを、統制の骨格として最初に共有しておく（詳細は
  [04](04-ガバナンス.md)・[05](05-セキュリティ法務調達.md)・[08](08-IT部門向けAIエージェント.md)・
  [10](10-パイロット運営.md)）。
- **判断ゲートの考え方**: 一定期間後、実測データをもとに次の段階を判断する、という**進め方
  そのもの**を最初に決めておく（[11](11-段階導入ロードマップ.md)）。ここで大事なのは「測定して
  から判断するという**手順**を先に決めておくこと」であり、「Enterprise化する」「Bedrock/Foundry
  に移行する」という**特定の結論に進むこと**をあらかじめ決めるものではない。Go（Enterprise化）／
  Go（Bedrock・Foundry検討）／Hold（現状維持）／Stop（中止）は対等な選択肢であり、この時点では
  どれも既定路線にしていない（判断基準の詳細は[11](11-段階導入ロードマップ.md)3.2節）。
- **費用の考え方**: 座席単価に対して必要な削減時間は小さく、損益分岐点は低い水準にあるという
  考え方で試算する（詳細な試算式・数値例は[02](02-費用対効果.md)）。

## 1. 想定読者と環境

- 非IT中小企業（100〜500人）。社内SE部門5〜15名、専任の情報システム部門というより兼務中心の小規模IT部門であり、開発主体ではない。
- 全社導入はハードルが高く、まずIT部門で小規模導入して効果を最大化したい。
- Claude 導入を主に想定（Codex/OpenAI も同等に扱う）。

## 2. なぜ今、小さく始めるのか

AI活用は、①チャットのような個人利用から、②社内情報に基づく回答・資料生成、③ツールを使った
自律的な複数手順の実行、そして④業務プロセスの構造自体がAIの存在を前提に組み替わる段階へと、
組織の理解と統制の成熟に応じて進んでいく（[12](12-AI活用の全体像.md)）。

④の段階に到達するかどうかは、この資料の主題ではない。ただし、①〜③の段階を経験しないまま
④を目指すことはできず、④に必要な統制設計（情報の同一性を保ったまま扱う仕組み、権限設計、
業務プロセスの見直し）は、①〜③の段階で得られる実務知見の上にしか成立しない
（[05](05-セキュリティ法務調達.md)2.4節）。

一方で、個人アカウントでのAI利用（シャドーAI）は、①の段階としてすでに現在進行形で起きている
可能性が高く、この現状は「導入するかどうか」の検討を待ってくれない（詳細と出典は
[01](01-導入判断.md)3.1節）。①を無管理のまま放置するか、統制のもとで①〜③の足場を作るかは、
次節で論点を整理する。

## 3. 本プロジェクトの立場

- 論点は「導入 vs 不導入」ではなく「**無管理の利用 vs 管理された利用**」（→ [01](01-導入判断.md)）。
  すでに個人アカウントでの利用（シャドーAI）が起きているなら、不導入という選択肢は
  実質的に「無管理のまま放置する」ことを意味する。
- 「学習しない法人プラン」でも**社外送信そのもの**は残る。ポリシーは後者基準（→ [05](05-セキュリティ法務調達.md)）。
- IT部門が触っていないのに、エージェントの提案・設計・リスク評価はできない。まず小規模IT部門限定で
  導入し知見を上げ、次段階（Enterprise / Bedrock / Foundry）を判断ゲートで決める（→ [11](11-段階導入ロードマップ.md)）。

## 4. 反論への回答（想定される質問）

| 想定される反論 | 回答 |
| --- | --- |
| 社内情報を外部AIに出すのは危険では | 学習利用と社外送信は別問題。法人プランは学習に使わない前提で、他のクラウドサービスと同じ基準（開示リスク）で管理可能（[01](01-導入判断.md)2.1節、[05](05-セキュリティ法務調達.md)） |
| 精度が不安・誤りが混ざるのでは | 下書き・レビュー前提の用途から始め、無検証で使わない運用にする（[01](01-導入判断.md)2.2節） |
| うちの業務は特殊でAIが向かないのでは | 汎用作業（文章・調査・コード）は業種非依存で効果が出やすく、そこから着手する（[01](01-導入判断.md)1.3節） |
| 費用に見合うのか | 座席単価に対し、必要な削減時間は月間1人あたり1時間程度と少なく、損益分岐点は低い水準にある試算。実測値は3〜6ヶ月後の判断材料にする（[02](02-費用対効果.md)） |
| 小規模IT部門限定は中途半端では | 妥協ではなく、次の投資判断に必要な知見を集める情報収集フェーズという設計（[06](06-製品プラン比較.md)3節、[11](11-段階導入ロードマップ.md)1節） |
| どうせ全社のシャドーAIは解決しないのでは | その通りで、小規模IT部門限定導入だけでは解決しない。全社的な統制は別途必要（[01](01-導入判断.md)3.3節、[04](04-ガバナンス.md)）。ただしまず小規模IT部門が統制の実務知見を持つことが前提になる |
| ただでさえ忙しい小規模IT部門に、教育・運用・測定までやる余裕があるのか | 強制利用ではなく希望者から開始し、運用工数（教育・例外対応・月次測定）は次の段階に進む場合にも必要になる知見を先取りする投資と位置づける（[02](02-費用対効果.md)3節、[10](10-パイロット運営.md)1.4節） |
| 教育・運用が定着せず利用率が上がらないのでは | 利用率低迷を明示的な停止条件の一つとしてあらかじめ定義する（[10](10-パイロット運営.md)1.3節） |

## 5. 検討のポイント・次のアクション

- 最初の30日で初期設定・教育を行い、5指標（[10](10-パイロット運営.md)、
  [11](11-段階導入ロードマップ.md)3節）のうちベースラインを持つ指標（時間削減・シャドーAI利用）の
  導入前値を記録する（[11](11-段階導入ロードマップ.md)2節のフェーズ1表）。
- 60〜90日で事後値・都度記録の指標（入力の詰まり・権限越境・他部署要望）を計測して中間集計する。
- 3〜6ヶ月後、その実測データをもとに次の段階（[11](11-段階導入ロードマップ.md)3.2節のGo/Hold/Stop
  の4択）を判断する。
- 社内で合意形成する際は、この資料の内容を稟議書の形式に落とし込んだ雛形
  （[付録](appendix/ringi-draft.md)）を出発点として使える。

## 留意点・免責

- 一般的な整理であり、法務・税務・セキュリティの最終判断は専門家・公式情報の確認が必要。
- 費用試算・タイムラインは読者の組織の状況に応じて置き換えること（[02](02-費用対効果.md)、[11](11-段階導入ロードマップ.md)）。
