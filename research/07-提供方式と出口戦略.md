# 07 提供方式・アーキテクチャ・出口戦略

法人SaaS・AWS Bedrock・Microsoft Foundry・API——同じAIモデルを使っていても、提供方式が違えば
統制の効かせ方もコスト構造もまったく別物になる。提供方式は大きく4つある。導入が最も速く統制も
揃う**法人SaaS**、既存のクラウド契約内で完結しやすい**Bedrock/Foundry/Vertex経由**、用途特化で
運用力が要る**API直接**、そして本記事では扱わない**オンプレ／ローカルLLM**だ。結論はシンプルで、
通常業務は法人SaaS（[05](05-セキュリティ法務調達.md)3節の層A）、機微度が高い領域は自社クラウド
経由（同・層B）という2階層で回すのが実務的（2節・4節）。パイロットは層Aから始め、
[10](10-パイロット運営.md)の指標2（入力しようとして詰まった情報の種類）で層Bが必要な領域が
見えた時点で、層Aを層Bに置き換えるのではなく、層Aを維持したまま層Bを追加導入する併用構成を
検討する（4節、判断基準は[11](11-段階導入ロードマップ.md)3.2節の3つの問いのうち「層B導入」）。

どの提供方式を選んでも、価格改定・モデル廃止・ベンダー障害・契約終了時のデータ削除確認といった
出口戦略（ロックイン対策）は導入前に決めておく（3節）。後回しにすると、いざ切り替えたいときに
身動きが取れなくなる。

プラン機能の詳細は[06](06-製品プラン比較.md)に譲る。対象は日本の法人契約とし、プラン・地域で
成立条件が変わる主張は適用条件を併記する。

## 1. 提供方式の位置づけ

| 提供方式 | 特徴 | 主な用途 |
| --- | --- | --- |
| 法人SaaS（Claude Team/Enterprise、ChatGPT Business/Enterprise） | 導入が最も速く、管理画面から統制機能を設定できる。座席課金 | 通常業務〜社外秘（マスキング前提）。[06](06-製品プラン比較.md) |
| Amazon Bedrock | AWS環境内でAnthropic等のモデルを利用。既存AWS契約・IAMと統合しやすい（[AWS「Identity and access management for Amazon Bedrock」][ref-aws-bedrock-iam]、確認日: 2026-07-14） | 顧客データ・個人情報を含む処理（AWS環境内で完結させたい場合） |
| Microsoft Foundry（Azure OpenAI含む） | Azure環境でOpenAI・Anthropic等のモデルを利用。既存Azure契約・Entra IDと統合しやすい。Claude利用時はHosted on Azure／Hosted on Anthropicの2構成があり、Azure内に留まるのは前者のみ（1.1節参照、[Microsoft Learn「Authentication and authorization in Microsoft Foundry」][ref-msft-foundry-auth]、確認日: 2026-07-14） | 同上（Azure中心の環境） |
| Google Vertex AI | Google Cloud環境内で各社モデルを利用（[Claude Platform Docs「Claude on Google Cloud」][ref-claude-vertex]、確認日: 2026-07-14） | 同上（GCP中心の環境） |
| API直接（Anthropic API / OpenAI API Platform） | ベンダーのAPIを直接従量課金で利用。座席の概念がない | 特定用途への組み込み、独自アプリケーション開発 |

### 1.1 データ所在の成立条件（要点、詳細は05参照）

- **Amazon Bedrock**: モデル提供元はBedrock上のプロンプト・応答にアクセスできない構成になっている
  （[AWS「Data protection」（Amazon Bedrock User Guide）][ref-aws-bedrock-dataprotection]、確認日: 2026-07-14）。
  コンテンツはモデルの改善にも使われない（[AWS「Amazon Bedrock FAQs」][ref-aws-bedrock-faq]、確認日: 2026-07-14）。
  ただし「AWSリージョン内で完結する」と言えるのは**単一リージョンでの呼び出し**、または特定の
  地理的範囲に限定した**Geographic cross-Region inference**を選んだ場合に限られる。Geographic
  cross-Region inferenceは既定では呼び出し元リージョンにのみデータを保存するが、処理自体は
  同一地理的範囲内の別リージョンに移動しうるほか、不正利用検知の対象モデルでは処理先リージョンにも
  データが保存される。**Global cross-Region inference**を選ぶと、世界中の対応リージョンへ処理が
  移動しうる（[AWS「Geographic cross-Region inference」][ref-aws-bedrock-geo-cris]、
  [AWS「Increase throughput with cross-Region inference」][ref-aws-bedrock-cris]、確認日: 2026-07-15、
  詳細は[05](05-セキュリティ法務調達.md)3節）。
- **Microsoft Foundry**: デプロイ時に**Hosted on Azure**（Azureインフラ上でAnthropicが運用する
  サービス）と**Hosted on Anthropic**（Anthropicインフラ上でAnthropicが運用するサービス）の
  2つのホスティング形態から選択する。**Azure内に留まるのは前者（Hosted on Azure）のみ**で、
  プロンプト・応答はAzure内に留まり、Anthropicには使用状況メタデータと安全システムがフラグした
  コンテンツのみが渡る。Hosted on Anthropicを選ぶと、推論はAnthropicのインフラ上で実行されるため
  「Azure内に留まる」という前提は成立しない（利用できるモデルの幅は広がる）。既定はモデルにより
  異なり、両対応モデルではHosted on Azureが既定だが、機微データを扱う場合は**デプロイ設定で
  Hosted on Azureを選んでいるか必ず確認する**（[Claude Platform Docs「Claude in Microsoft
  Foundry」][ref-claude-foundry]、確認日: 2026-07-14）。
- **Google Vertex AI**: データの取り扱いはGoogle Cloudが管理する
  （[Claude Platform Docs「Claude on Google Cloud」][ref-claude-vertex]、確認日: 2026-07-14）。

いずれも「クラウド境界内で完結」は**成立条件付きの事実**であり、実際の契約構成・リージョン設定を
確認して初めて言える（[用語集](../docs/glossary.md)「クラウド境界内」参照。各社の詳しい保持期間・
サブプロセッサー等の条件は[05](05-セキュリティ法務調達.md)3節にまとめている）。

## 2. 比較（用途・運用能力・TCO）

| 観点 | 法人SaaS | AWS Bedrock | Microsoft Foundry | API直接 |
| --- | --- | --- | --- | --- |
| データ所在 | ベンダー既定（[06](06-製品プラン比較.md)のデータレジデンシー欄参照） | **単一リージョン呼び出し時はAWSリージョン内。Geographic cross-Region inferenceでは同一地理的範囲内、Globalでは世界の対応リージョンへ処理が移動しうる**（1.1節、成立条件は05参照） | **Hosted on Azure選択時のみAzure内**。Hosted on Anthropic選択時はAnthropic側インフラで推論（1.1節、成立条件は05参照） | ベンダー既定 |
| 課金単位 | 座席課金＋一部利用量 | トークン従量課金（AWS請求に統合、[AWS Bedrock Pricing][ref-aws-bedrock-pricing]、確認日: 2026-07-14） | トークン従量課金（Anthropicのモデル別単価をClaude Consumption Units（CCU）に換算し、1時間単位でメータリングしてAzure請求に統合。CCU自体はプリペイド残高ではなく、時間課金の対象は換算後のメータリングのみ。[Microsoft Learn「Claude consumption units (CCU) billing」][ref-msft-foundry-ccu]、確認日: 2026-07-14） | トークン／クレジット従量課金 |
| 最低契約規模 | Claude Enterprise: 20席〜（self-serve）／50席〜（営業経由、[Claude Help Center][ref-claude-enterprise]、確認日: 2026-07-14）。ChatGPT Business: 2名〜（[ChatGPT Pricing][ref-chatgpt-pricing]、確認日: 2026-07-13） | 座席概念なし（従量課金） | 座席概念なし（従量課金、プリペイド残高やコミットメントは不要。[Microsoft Learn「CCU billing」][ref-msft-foundry-ccu]） | 座席概念なし |
| 統制・監査 | 管理画面から設定（[06](06-製品プラン比較.md)2.2節） | AWS IAM・CloudTrailと統合（[AWS「IAM for Bedrock」][ref-aws-bedrock-iam]） | Azure Entra ID・RBACと統合（[Microsoft Learn「認証・認可」][ref-msft-foundry-auth]） | 自前で構築が必要 |
| 必要な運用能力 | 低い（管理画面操作が中心） | 中〜高（AWS運用知識が必要） | 中〜高（Azure運用知識が必要） | 高い（API統合・レート制御等を自前で実装） |
| 向く用途 | 通常業務、小規模IT部門限定パイロットの初期段階 | 顧客データ・個人情報を扱う業務、AWS中心の環境 | 同上（Azure中心の環境） | 独自アプリへの組み込み |

各項目の詳細な一次情報は [05](05-セキュリティ法務調達.md)・[06](06-製品プラン比較.md) と本記事末尾の
参考文献を参照。料金・仕様は変動するため確認日を必ず併記する。

## 3. 出口戦略（ロックイン対策）

提供方式を選ぶ前に、次の観点を必ず確認しておく。

- **価格改定リスク**: 座席単価・従量課金レートは変更され得る（[06](06-製品プラン比較.md)2.1節で、
  ChatGPT Businessの座席単価が改称とは別時期に引き下げられた例を確認）。契約更新時の価格変動条項を確認する。
- **モデル廃止・世代交代**: 利用中のモデルが将来廃止される可能性がある。移行時の互換性・
  再学習/再設定コストを見込んでおく。
- **データ移行・可搬性**: 会話履歴・カスタム設定・ナレッジベース等を他サービスへ移行できるか
  （エクスポート機能の有無）。
- **契約終了時の削除確認**: 契約終了後、ベンダー側に残るデータ（保持期間中のログ等）が
  確実に削除されるか。DPA・契約書の削除条項を確認する（[05](05-セキュリティ法務調達.md)6節）。
- **障害・利用上限・ベンダー停止時の業務継続**: 単一ベンダーへの依存度が高い業務は、代替手段
  （別ベンダーへの切り替え、一時的な人手対応）を用意しておく。
- **構成図・責任分界の文書化**: 提供方式ごとに「どこまでベンダーの責任か、どこから自社の責任か」を
  明文化しておく（監査対応にも使う、[11](11-段階導入ロードマップ.md)4節）。

## 4. 使い分けの指針

- **通常業務はSaaS（層A）から始める**。導入が速く、小規模IT部門限定パイロットの初期段階に適している。
- **機微度が高い領域（顧客データ・個人情報を扱う業務）が明確になった時点で層B（Bedrock/Foundry/
  Vertex）を検討する**。既に自社がAWS中心かAzure中心かで、親和性の高い方を選ぶのが合理的。
  クラウド既存契約（AWS/Azure/GCP）の有無・種別によって層Bの導入しやすさは大きく変わるため、
  自社の既存契約状況を踏まえて判断する。
- 提供方式の選択は一度決めたら終わりではなく、[11](11-段階導入ロードマップ.md) の見直しのタイミング
  （3〜6ヶ月後）でパイロットの実測データ（特に指標2「入力しようとして詰まった情報の種類」）を
  もとに再検討する。

## 検討のポイント

- パイロット段階では法人SaaS（層A）で開始し、出口戦略チェックリストだけは最初に確認しておく
  （後から追加するより最初に決めておくほうが安い）。対応モデル・リージョン・料金体系は変動するため、
  稟議・契約の直前に必ず再確認する。
- 層B（Bedrock/Foundry/Vertex）の追加導入（層Aとの併用、置き換えではない）は、
  [11](11-段階導入ロードマップ.md) の見直しのタイミングで、パイロットの実測データをもとに
  検討する（3.2節の問い3「層B導入」）。
