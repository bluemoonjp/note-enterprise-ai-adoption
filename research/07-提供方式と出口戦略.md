# 07 提供方式・アーキテクチャ・出口戦略

法人SaaS・AWS Bedrock・Microsoft Foundry・API——同じAIモデルでも、提供方式によって統制・コスト
構造は大きく変わる。この記事はその使い分けと、出口戦略（ロックイン対策）を扱う。プラン機能の
詳細は[06](06-製品プラン比較.md)に譲る。対象は日本の法人契約とし、プラン・地域で成立条件が
変わる主張は適用条件を併記する。

## 要約（結論先出し）

- **結論: 通常業務は法人SaaS（層A）、機微度が高い領域は自社クラウド経由の層B
  （Bedrock/Foundry/Vertex）という階層構成が実務的**（[05](05-セキュリティ法務調達.md)3節と
  同じ考え方、2節・4節）。層A＝法人SaaS、層B＝自社クラウド経由、層C＝オンプレ・ローカルLLM
  （本記事の対象外）の3層。
- 根拠: 提供方式は大きく4つ：**法人SaaS**（導入が速く統制も揃う、層A）、**Bedrock/Foundry/
  Vertex経由**（既存クラウド契約内で完結しやすい、層B）、**API直接**（用途特化・運用能力が要る）、
  **オンプレ／ローカルLLM**（層C、本記事では対象外）（1節）。
- 反論への回答: どの提供方式を選んでも、**出口戦略（ロックイン対策）を導入前に決めておく**必要がある。
  価格改定・モデル廃止・ベンダー障害・契約終了時のデータ削除確認は、後回しにすると
  身動きが取れなくなる（3節）。「導入方式を間違えたら後戻りできないのでは」という懸念には、
  出口戦略チェックリスト（3節）で応える。
- 次のアクション: パイロットは層A（法人SaaS）から始め、指標2（[10](10-パイロット運営.md)）で
  層Bが必要な領域が見えた時点で切り替えを検討する（4節）。

## 1. 提供方式の位置づけ

| 提供方式 | 特徴 | 主な用途 |
| --- | --- | --- |
| 法人SaaS（Claude Team/Enterprise、ChatGPT Business/Enterprise） | 導入が最も速く、管理画面から統制機能を設定できる。座席課金 | 通常業務〜社外秘（マスキング前提）。[06](06-製品プラン比較.md) |
| Amazon Bedrock | AWS環境内でAnthropic等のモデルを利用。既存AWS契約・IAM等と統合しやすい | 顧客データ・個人情報を含む処理（AWS環境内で完結させたい場合） |
| Microsoft Foundry（Azure OpenAI含む） | Azure環境内でOpenAI・Anthropic等のモデルを利用。既存Azure契約・Entra ID等と統合しやすい | 同上（Azure中心の環境） |
| Google Vertex AI | Google Cloud環境内で各社モデルを利用 | 同上（GCP中心の環境） |
| API直接（Anthropic API / OpenAI API Platform） | ベンダーのAPIを直接従量課金で利用。座席の概念がない | 特定用途への組み込み、独自アプリケーション開発 |

### 1.1 データ所在の成立条件（要点、詳細は05参照）

- **Amazon Bedrock**: モデル提供元はBedrock上の顧客データにアクセスできない構成（AWS側の
  Model Deployment Accountで分離）。データはBedrockが稼働するAWSリージョン内で暗号化・保存される
  （[05](05-セキュリティ法務調達.md)3節、出典同記事参照）。
- **Microsoft Foundry**: プロンプト・応答はAzure内に留まり、モデル提供元には（許可なく）渡らない。
  Claude on Microsoft Foundryの場合、Anthropicには使用状況メタデータと安全システムがフラグした
  コンテンツのみが渡る（[05](05-セキュリティ法務調達.md)3節）。
- **Google Vertex AI**: データ取り扱いはGoogle Cloudが管理する構成（[05](05-セキュリティ法務調達.md)3節）。

いずれも「クラウド境界内で完結」は**成立条件付きの事実**であり、実際の契約構成・リージョン設定を
確認して初めて言える（[用語集](../docs/glossary.md)「クラウド境界内」参照）。

## 2. 比較（用途・運用能力・TCO）

| 観点 | 法人SaaS | AWS Bedrock | Microsoft Foundry | API直接 |
| --- | --- | --- | --- | --- |
| データ所在 | ベンダー既定（[06](06-製品プラン比較.md)のデータレジデンシー欄参照） | AWSリージョン内（成立条件は05参照） | Azure内（成立条件は05参照） | ベンダー既定 |
| 課金単位 | 座席課金＋一部利用量 | トークン従量課金（AWS請求に統合） | Claude Consumption Units等、時間課金でAzure請求に統合 | トークン／クレジット従量課金 |
| 最低契約規模 | Claude Enterprise: 20席〜（self-serve）／50席〜（営業経由）。ChatGPT Business: 2名〜 | 座席概念なし（従量課金） | 座席概念なし（従量課金、コミットメント不要） | 座席概念なし |
| 統制・監査 | 管理画面から設定（[06](06-製品プラン比較.md)2.2節） | AWS IAM・CloudTrail等の既存統制と統合 | Azure Entra ID・監査ログ等の既存統制と統合 | 自前で構築が必要 |
| 必要な運用能力 | 低い（管理画面操作が中心） | 中〜高（AWS運用知識が必要） | 中〜高（Azure運用知識が必要） | 高い（API統合・レート制御等を自前で実装） |
| 向く用途 | 通常業務、小規模IT部門限定パイロットの初期段階 | 顧客データ・個人情報を扱う業務、AWS中心の環境 | 同上（Azure中心の環境） | 独自アプリへの組み込み |

（各項目の一次情報は [05](05-セキュリティ法務調達.md)・[06](06-製品プラン比較.md) を参照。
料金・仕様は変動するため確認日を必ず併記する。）

## 3. 出口戦略（ロックイン対策）

提供方式を選ぶ前に、次の観点を必ず確認しておく。

- **価格改定リスク**: 座席単価・従量課金レートは変更され得る（[06](06-製品プラン比較.md)2.1節で、
  ChatGPT Businessの座席単価が改称とは別時期に引き下げられた例を確認）。契約更新時の価格変動条項を確認する。
- **モデル廃止・世代交代**: 利用中のモデルが将来廃止される可能性がある。移行時の互換性・
  再学習/再設定コストを見込んでおく。
- **データ移行・可搬性**: 会話履歴・カスタム設定・ナレッジベース等を他サービスへ移行できるか
  （エクスポート機能の有無）。
- **契約終了時の削除確認**: 契約終了後、ベンダー側に残るデータ（保持期間中のログ等）が
  確実に削除されるか。DPA・契約書の削除条項を確認する（[05](05-セキュリティ法務調達.md)6節）。
- **障害・利用上限・ベンダー停止時の業務継続**: 単一ベンダーへの依存度が高い業務は、代替手段
  （別ベンダーへの切り替え、一時的な人手対応）を用意しておく。
- **構成図・責任分界の文書化**: 提供方式ごとに「どこまでベンダーの責任か、どこから自社の責任か」を
  明文化しておく（監査対応にも使う、[11](11-段階導入ロードマップ.md)4節）。

## 4. 使い分けの指針

- **通常業務はSaaS（層A）から始める**。導入が速く、小規模IT部門限定パイロットの初期段階に適している。
- **機微度が高い領域（顧客データ・個人情報を扱う業務）が明確になった時点で層B（Bedrock/Foundry/
  Vertex）を検討する**。既に自社がAWS中心かAzure中心かで、親和性の高い方を選ぶのが合理的。
- 提供方式の選択は一度決めたら終わりではなく、[11](11-段階導入ロードマップ.md) の判断ゲート（3〜6ヶ月後）で
  パイロットの実測データ（特に指標2「入力しようとして詰まった情報の種類」）をもとに再検討する。

## 検討のポイント

- パイロット段階では法人SaaS（層A）で開始し、出口戦略チェックリストだけは最初に確認しておく
  （後から追加するより最初に決めておくほうが安い）。
- 層B（Bedrock/Foundry/Vertex）への移行は、[11](11-段階導入ロードマップ.md) の判断ゲートで、パイロットの
  実測データをもとに検討する。

## 留意点・免責

- 対応モデル・リージョン・料金体系は変動する。確認日を必ず併記し、稟議・契約直前に再確認すること。
- クラウド既存契約（AWS/Azure/GCP）の有無・種別によって、層Bの導入しやすさは大きく変わる。
  自社の既存契約状況を踏まえて判断すること。
