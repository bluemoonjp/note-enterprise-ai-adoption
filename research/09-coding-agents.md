## 要約（結論先出し）

- 小規模開発は行うがモダンな開発手法（バージョン管理・レビュー・CI）が定着していない部門でも、
  コーディングエージェント（[用語集](../docs/glossary.md)参照）により**定型スクリプト・データ処理・
  社内ツールの内製スピード**を大きく上げられる（2節）。
- ただし効果を安全に得るには、**導入前提となる最低限の開発統制**（Git・コードレビュー・
  秘密情報検知・実行環境分離）を先に整える必要がある（3節）。統制なしにエージェントの
  実行権限だけを広げるのは危険。
- 「機密ファイルを自動で除外する仕組みがある」という理解は誤りで、**明示的な除外設定が必要**
  （よくある誤解、詳細は3.2節）。

## 1. 前提：この部門の現状

想定する情シス部門は、小規模な開発（簡易ツール・スクリプト作成等）は行っているものの、
バージョン管理（Git）・コードレビュー・自動テスト・CI（継続的インテグレーション）といった
**モダンな開発手法が定着していない**ことが多い。属人化した「動けばよい」スクリプトが、
担当者しか把握していない状態で本番運用されているケースも珍しくない。

## 2. 何が変わるか・何ができるようになるか

- **内製化の範囲が広がる**: これまで「外注するほどでもないが自分で書く時間もない」という理由で
  見送られていた小規模開発・自動化が、内製で対応しやすくなる。
- **属人運用のコード化・再現性向上**: 担当者の頭の中にしかなかった手順が、コードとドキュメントとして
  残りやすくなる（コーディングエージェントは説明・ドキュメント生成も得意）。
- **モダンな開発手法への移行の敷居が下がる**: コードレビューやテストコードの作成自体を
  エージェントに補助させることで、「導入したいが手が回らない」だった改善に着手しやすくなる。

これらは「開発者がいなくても開発できる」という意味ではなく、**開発の初速・下書きの質が上がる**
という意味である。最終的な正しさの確認・意思決定は引き続き人が担う（[01](01-adoption-criteria.md)2.2節）。

## 3. 導入前提となる開発統制

コーディングエージェントは、一般的なチャット型AIと異なり、**ファイルの読み書き・コマンド実行**を
伴う場合がある。効果を安全に得るには、次の統制を導入前提として整備する。

### 3.1 基本の開発統制

- **バージョン管理（Git）**: 変更履歴を残し、意図しない上書き・喪失を防ぐ。
- **コードレビュー**: エージェントが生成したコードも、人によるレビューを必須にする
  （[01](01-adoption-criteria.md)2.2節の「精度懸念は運用で管理する」の実践）。
- **テスト**: 最低限の動作確認（手動でも可）を、本番反映前のルールとして定める。
- **依存関係の確認**: 追加されたライブラリ・パッケージの出所・ライセンスを確認する。

### 3.2 機密情報の除外設定

**「`.claudeignore`で機密ディレクトリを自動除外できる」という理解は誤り**であり、Claude Codeに
そのような公式機能は存在しない（2026-07-13時点で確認）。機密ファイル・ディレクトリの除外は、
`settings.json` の `permissions.deny` にファイル読み取りの拒否パターンを明記する方式が正式である
（例: `"deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]`、
[Claude Code Docs「Settings」][ref-claudecode-settings]、確認日: 2026-07-13）。

ただし、Bashコマンド経由で間接的にファイル内容へアクセスできる可能性が理論上あるため、
**権限設定だけに頼らず、サンドボックス化・実行環境分離と併用する**（[05](05-security-legal-procurement.md)5節）。

### 3.3 データ送信に関わる設定

- **`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` 環境変数**: テレメトリ・エラーレポート・`/feedback`
  関連の追加通信など、非必須のトラフィックを抑止できる（[05](05-security-legal-procurement.md)5節）。
- **`/feedback` コマンドの扱い**: 実行すると会話履歴（コードを含む）がAnthropicに送信される。
  社内では原則禁止とし、必要な場合のみ個別許可する運用が無難（[05](05-security-legal-procurement.md)5節）。
- **リポジトリ側のシークレットスキャン**: APIキー・認証情報の混入を、コード側でも検知する仕組みを
  併用する。

### 3.4 実行環境の分離

エージェントにコマンド実行権限を与える場合、本番環境と切り離した開発・検証環境で運用する。
特に、社内システムへの書き込み・設定変更を伴う自動化は、人によるHITL承認を挟む
（[08](08-it-dept-agents.md)4.3節と同じ考え方）。

- 最低限の開発統制チェックリスト（Git・レビュー・テスト・秘密情報検知・環境分離）
- コーディングエージェント用パイロット計画（対象者・対象業務・除外設定・環境分離の確認項目）

## 自社（情シス小規模導入）への当てはめ

- 一般AI導入（文章・調査用途）のパイロットと並行し、コーディングエージェントは**別トラック**として、
  対象者（実際にスクリプト作成を行うメンバー）を絞って開始する。
- 導入前に、最低限のGit運用・レビュー体制・機密ファイルの除外設定（3.2節）を整える。
  「使いながら統制を整える」のではなく、**統制を先に整えてから使い始める**順序を守る。
- `/feedback`の利用可否、シークレットスキャンの導入は、開発統制チェックリストの必須項目にする。

## 留意点・免責

- 製品のサンドボックス仕様・除外設定・データ取り扱いは変動する。確認日と一次情報を必ず確認すること。
- 本記事はClaude Codeを中心に記載しているが、Codex（OpenAI）等の同種製品にも同様の考え方が
  当てはまる。個別の設定方法は各製品の公式ドキュメントを確認すること。
