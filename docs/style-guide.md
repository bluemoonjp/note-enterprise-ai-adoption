# 執筆・出典スタイルガイド

本プロジェクトの調査記事を書くときの共通ルール。作業ルールの正本は
[../AGENTS.md](../AGENTS.md)、本ファイルはその「執筆・出典」の詳細版。

## 1. 基本方針

- **読者は非IT中小企業の小規模IT部門／社内SEと、導入を判断する上層（経営層・意思決定者）**の二層。
  専門用語は初出時に一言で補足するか [用語集](glossary.md) に誘導する。
- 本プロジェクトの成果物は、特定の自社向けの提案書ではなく**汎用解説資料**であり、中立的な調査
  論文でもない。想定読者の組織を一つのモデルケースとして扱いながら、実務レベルの判断に使える
  具体性を保つ。「結論 → 根拠（出典）→ 反論への回答 → 検討のポイント・次のアクション」の順を
  基本とする（詳細は1.1節）。
- **事実と解釈を分ける**。出典で裏付く事実と、本プロジェクトとしての推奨・解釈を
  段落や見出しで区別する（例: 「事実」「本プロジェクトの見解」）。
- **出典が無いことを理由に、伝えるべき主張・推奨を削らない**。事実（価格・仕様・各社ポリシー等）
  は出典必須だが、本プロジェクトの推奨・判断・自社への当てはめは出典不要（3.5節）。網羅性・
  説得力を優先し、「安全に書ける範囲に縮小する」方向に倒さない。

## 1.1 説得構成の章立て（上層向けパートの基本形）

上層向けに読ませる章（`00` 概要、各記事の冒頭・検討のポイント節など）は次の順で書く。

1. **結論**（先出し）: 何を・なぜ・どの順で導入すべきか。**専用の見出し・箇条書きセクションを
   設けず**、記事冒頭1〜2段落の自然な文章で示す（4節）。
2. **根拠**: 出典付きの事実、費用対効果、放置した場合のリスク（シャドーAI等）。
3. **反論への回答**: 「導入しない口実にされがちな要因」を先回りして潰す
   （→ [01](../research/01-導入判断.md)）。想定される反論を明示し、それぞれに回答する。
4. **検討のポイント・次のアクション**: 具体的な次の90日、判断ゲート（見直しのタイミング）、
   社内合意形成の際に確認すべき事項。

小規模IT部門内向けの深掘り部分（本論）は、この結論を裏付けるための実務レベルの詳細
（統制の実装方法・比較表・手順）を必要十分な深さで書く。省略しすぎて「結局何をすればいいか
わからない」状態にしない。

## 1.1.1 反論への回答・リスク言及の非対称を作らない

本プロジェクトの想定読者は「積極的にAI活用したいが、どうしていいか分からない・やり方が
ズレている会社」であり、懐疑的な会社を説得する資料ではない。出典必須ルール（AGENTS.md）を
守りながらも、次の点で「懸念だけが強調され、前進の後押しが弱い」非対称を作らないようにする。

- 懸念・リスクを述べる段落は、**懸念の提示 → 出典 → 対応・解決**を同一段落内（遅くとも
  直後の1段落以内）で完結させる。懸念だけで段落を終えない。
- ポジティブな数値（効果・生産性等）とネガティブな数値（失敗率・中止率等）に「二次情報である」
  等の注記を付ける場合は、**両方に同じ厚み・同じ位置**で付ける。片方だけを深掘りで打ち消し、
  もう片方は無傷のままにしない。
- 懸念を打ち消す文（「裏を返せば」「ただし」等）は懸念の**直後**に置く。複数段落を挟んでから
  初めて解決文が出る構成にしない。
- 章・節の書き出しを「〜を楽観視しすぎない」等の評価的な負のフレーミングから始めない。
  結論・事実を先に述べる（本節冒頭の「結論→根拠」原則と整合させる）。
- 「AをやってからでないとBはできない」のような、対象範囲・影響範囲（blast radius）を
  考慮しない全社一律・全ケース一律の絶対的な統制順序ルールは、段階的な表現
  （最低限は初日から、それ以外は利用範囲拡大に合わせて追加、等）に言い換えられないか確認する。
- **将来の投資判断（Enterprise化・Bedrock/Foundry検討等）を確定事項のように書かない**。
  「測定して判断する**プロセス**を約束する」ことと、「特定の結論（Enterprise化する等）に
  **進む**ことを約束する」ことは別物であり、混同しない。判断ゲートでの選択肢
  （Go/Hold/Stop等）は対等な選択肢として書き、そのうちの一つを既定路線であるかのように書かない。

これらは事実・出典・免責文言を削ることを意味しない。並び順・接続・重みづけの調整で対応する。

## 2. 出典（最重要）

- 事実・数値・各社仕様・認証取得状況などの主張には、**一次情報**への出典を付ける。
  - 一次情報の優先順: 各社の公式ドキュメント / 公式料金ページ / Trust Center /
    公式ブログ・プレスリリース > 信頼できる二次情報。
  - 二次情報（まとめ記事等）だけで断定しない。使う場合も一次情報を併記する。
- **出典は本文中のインラインリンクと記事末尾の「参考文献」の両方に必ず記載する**（どちらか
  一方だけで済ませることは認めない）:
  1. 本文の該当箇所に **インラインリンク**（例: 「…学習に使わない（[OpenAI Enterprise Privacy][ref-oai-privacy]）」）。
  2. 記事末尾の **「参考文献」** に、可視のリンクとして一覧（タイトル・発行元・URL・確認日）。
     他記事へのリンクだけで済ませず、本文の主張を実際に裏付ける一次情報のURLを持たせる。
  - 書き手の裁量が働くのは「URLを本文にそのまま書き下すか、参照リンク形式
    （`[text][ref-xxx]`）で書くか」という**表記方法のみ**であり、インライン・参考文献の
    どちらかを省略してよいという意味ではない。
- リンク切れに備え、重要出典は**発行元名と文書名**をテキストでも残す（URLだけにしない）。

### 出典の書き方（例）

本文（参照スタイルのリンク推奨）:

```markdown
法人向けプランでは、入力データを既定でモデル学習に使用しないとされる（[OpenAI Enterprise Privacy][ref-oai-privacy]、2026-07-12 時点）。
```

末尾（参考文献は可視のリンク一覧にする。参照リンク定義だけでは描画時に節が空になるため不可）:

```markdown
## 参考文献

- [OpenAI — Enterprise privacy][ref-oai-privacy]（確認日: 2026-07-12）

[ref-oai-privacy]: https://openai.com/enterprise-privacy/
```

## 3. 鮮度・確認日

- 各社のプラン・価格・仕様・認証は数か月単位で変わる。**確認日を必ず併記**する。
  - 記事全体の確認日・再確認期限は記事本文には書かず、[research/README.md](../research/README.md)
    の記事インデックスに一元管理する（4節・AGENTS.md参照）。
  - 個別の可変情報には本文中に `（YYYY-MM-DD 時点）` を付ける。
- 「四半期ごとに見直す」ことを前提に書く（断定しすぎない）。可変情報が多い記事
  （05/06/07）は、稟議・公開の直前にも再確認する。

## 3.5 事実・推奨・仮定・例示の区別

主張は種類を明示して書き分ける（読者が意思決定に使えるようにする）。

- **事実**: 出典で裏付く。出典＋確認日を付ける。
- **本プロジェクトの判断（推奨）**: 前提条件・代替案・反対条件・撤退条件を併記する。
- **自社で確認すべき事項**: 未確定・要問い合わせ・法務確認など、読者側の宿題として明示。
- **例示/仮定**: マスキングし、仮定であることを明記。

出典は主張の種類ごとに優先情報源を使い分ける。

| 主張の種類 | 優先する一次情報 |
| --- | --- |
| 仕様・機能 | 各社公式ドキュメント・管理者向けヘルプ |
| 価格 | 公式料金ページ（通貨・税・契約期間・最低席数・従量課金の前提付き） |
| 効果・生産性 | 原研究・公的調査・第三者研究（ベンダー事例だけで断定しない） |
| 法務・規制 | e-Gov・所管官庁・個人情報保護委員会等の原典 |
| 認証 | 各社 Trust Center（対象サービス・適用範囲・有効期間まで） |
| 「なぜ今エージェントか」等の方向性・危機感 | Microsoft・Google・AWS・OpenAI・Anthropic 等の経営層・公式ブログでの発言（例: Satya Nadella 等）。**実在する一次ソース（発言日・媒体）を確認してから引用**し、存在しない・うろ覚えの引用は作らない。あくまで「業界の潮流」の裏付けであり、自社の判断根拠そのものにはしない（判断根拠は自社データ・パイロット結果を優先）。 |

## 3.6 比較表の書き方

- **空欄禁止**。「非対応」「不明」「要問い合わせ」「契約依存」を使い分ける。
- 比較は**同一確認日・同一比較軸**で行う。料金と機能は契約単位で区別する。
- 各セルに出典（または上記の状態）と確認日を持たせる。

## 3.7 誤解を招きやすい語

- 「学習しない」「クラウド境界内」等は**条件付き事実**。契約主体・機能・リージョン・保持・
  サブプロセッサーまで分解し、成立条件と非保証事項を明記する。
- 「学習利用／推論時処理／保存／ログ／保持／削除／サブプロセッサー提供」は**別概念**として区別する。
- ベンダーのマーケティング主張と、独立した効果検証を区別して記述する。

## 4. 記事フォーマット

**メタ情報（対象読者・問い・対象範囲・対象外・ステータス・確認日・再確認期限・関連Issue）は
記事本文には書かず、[research/README.md](../research/README.md) の記事インデックスに
一元管理する（AGENTS.md参照）。** 記事は読み物として、メタ情報ブロックなしに本文から始める。

各記事は次の骨格に従う。

```markdown
# <番号> <タイトル>

<冒頭1〜2段落: 読み物としての導入と、この記事固有の結論（何を・なぜ・どの順で、等）を、
見出しや箇条書きに切り出さず自然な文章で示す。この記事が答える問い・対象範囲・対象外の
正式な定義は記事本文には書かず research/README.md に一元管理するが、話題が他記事の範囲に
なる場合は本文中で自然に当該記事番号へ言及してよい。全体の位置づけ・投資判断ロジックの説明は
概要（00）・11に譲って繰り返さない（1.1.1節）。地域・契約形態で成立条件が変わる主張を扱う
記事（05/06/07等）は、対象地域・対象契約も本文中で明記する。>

## <本論の見出し>
本文（事実 → 出典 → 判断の順。事実・推奨・仮定・自社確認事項を区別）。法務・税務・投資判断・
セキュリティ設計に踏み込む箇所は、その場でインラインの一文注記を添える（6節）。

## 検討のポイント
- 想定環境に落とした具体的な示唆。読者が自らの組織に当てはめて考える際の視点。

## 記事末尾の成果物 / 判断結果
- 解説で終わらせず、チェックリスト・比較表・判断結果などの実務成果物を置く。

## 参考文献
- [発行元 — 文書名][ref-xxx]（対象製品/プラン/地域・確認日: YYYY-MM-DD）

[ref-xxx]: URL
```

## 5. 表記ルール

- 数値・金額・企業名の例示は**マスキング**（「A社」「X億円」等）。実在の顧客・取引先の
  固有名詞や非公開数値を書かない。
- 用語は [用語集](glossary.md) に集約。記事内で長い定義を繰り返さず、用語集へ誘導する。
- 単位・表記ゆれを避ける（「AIエージェント」「エージェント」など、記事内で統一）。
- 箇条書きと表を活用し、比較は表にする（プラン比較など）。

## 6. 免責の付け方

- 法務（NDA・個人情報保護法・越境移転）、税務・会計、投資判断、セキュリティ設計に踏み込む
  箇所は、該当箇所にその場で一文だけインラインの注記を置く。記事末尾の専用セクションには
  しない。
- **うち法務・税務・投資判断に関わる箇所は、AGENTS.mdの絶対ルール6により「専門家確認が
  必要」という趣旨を注記の内容に必ず含める**（`ref-xxx` 等の出典と同様、削ってよい情報では
  ない）。ただし要求されるのは趣旨であって同一文言ではない。「最終判断は専門家に確認すること」
  という一言一句を毎回コピーするのではなく、文脈に応じて表現を変えてよい（8節の「定型的な
  保険文言の反復」禁止は、この趣旨自体を省くことではなく、同じ言い回しを使い回すことを
  指す）。

## 7. レビュー観点（サブエージェント / Codex / 人間共通）

- 出典が一次情報か、**本文中のインラインリンクと記事末尾の参考文献の2か所の両方**に
  付いているか、参考文献が実際に本文の主張を裏付けるリンクになっているか（他記事への
  リンクだけで済ませていないか）。
- 断定的記述に確認日があるか。
- 事実と解釈が混ざっていないか。
- 出典が無いことを理由に、伝えるべき主張・推奨が削られていないか（削りすぎも指摘対象）。
- 上層が読んで結論・根拠・反論への回答が分かり、納得できる構成になっているか（説得力・論理構成）。
- 想定読者（小規模IT部門内／上層）それぞれにとって分かりやすく、実行可能な示唆になっているか。
- 各懸念・リスクの提示に、同等の重みの対応・前進の記述が近接して置かれているか
  （楽観と悲観の非対称な打ち消しになっていないか、1.1.1節）。
- 用語・表記の整合、内部リンク切れの有無。
- トーンが8節の方針（簡潔・直接・定型的な保険文言の反復なし・平易な日本語）に沿っているか。

## 8. トーン方針

- 短い段落・直接的な言い回しを基本にする。一文を長く畳み込まず、結論から書く。
- 「一般的な整理であり」のような、内容を伴わない定型的な保険文言を繰り返さない。免責が
  必要な箇所は6節の通りその場で一文だけ添える。ただし6節が求める「専門家確認が必要」という
  趣旨表示そのものを省いてよいという意味ではない。**禁止しているのは同一文言をそのまま
  使い回すこと**であって、内容（専門家確認を促すこと）は毎回必要である。表現だけを
  文脈に応じて変える。
- 普段使わない硬い専門用語・直訳的な言い回しは避け、平易な日本語に置き換える（読者が
  実務で使わない言葉は使わない）。ただし本プロジェクトの[用語集](glossary.md)に定義された
  確立語（例: 「判断ゲート」）は、記事群で既に統一運用されている用語であり、この対象では
  ない。
- 文体の参考として、[DevelopersIO](https://dev.classmethod.jp/) のようなIT系ブログ記事の
  簡潔さ・直接性を参考にする。持って回った言い回し・過度な前置きを避け、要点から書く。
