# 1. 全体設計

## 推奨する記事構成

- **00 エグゼクティブサマリ**
  - 経営判断、推奨案、主要リスク、概算費用、次の90日を1ページ相当に集約。
  - 他記事完成後に最後に執筆する。

- **01 導入判断とユースケース選定**
  - 導入／不導入の二択ではなく、用途別に「許可・条件付き・禁止」を判定。
  - 前提条件、停止条件、代替策も明示する。

- **02 ビジネスケース・費用・ROI**
  - ライセンス以外の教育、運用、監査、連携開発、レビュー工数を含むTCOで評価。
  - 時短だけでなく品質、処理量、リードタイム、リスク低減を扱う。

- **03 ガバナンス・社内規程・責任分担（新設）**
  - 利用規程、承認者、サービスオーナー、相談窓口、例外承認、インシデント対応、RACIを定義。

- **04 セキュリティ・プライバシー・法務・調達**
  - 情報分類、保持・削除、越境移転、DPA、サブプロセッサー、知的財産、監査対応を統合。
  - 法的結論ではなく「専門家へ確認する質問」に落とす。

- **05 製品・プラン別統制機能比較**
  - ベンダー別・契約形態別に、SSO、SCIM、ログ、保持、学習利用、コネクタ管理等を比較。
  - 不明、要問い合わせ、契約依存を明示する。

- **06 提供方式・アーキテクチャ・出口戦略**
  - SaaS／Bedrock／Foundry／APIを、用途・運用能力・総保有コストで比較。
  - ベンダーロックイン、モデル切替、データ移行、サービス終了時の対応を追加。

- **07 パイロット運営・教育・効果測定（再編）**
  - 対象者、対象業務、教育、サポート、測定方法、証跡、停止条件を定義。
  - 現行03の効果測定と09のパイロット部分を集約する。

- **08 IT部門向けAIエージェント**
  - 最小権限、権限越境、プロンプトインジェクション、コネクタ審査、人による承認を扱う。

- **09 コーディングエージェント**
  - Git、レビュー、テスト、秘密情報、依存関係、実行権限を導入前提として扱う。
  - 一般AI導入とは別のパイロットトラックにする。

- **10 段階導入ロードマップと判断ゲート（新設）**
  - 30／60／90日、3〜6か月の成果物と、拡大・継続・中止条件を明示する。

- **付録（実務テンプレート）**
  - 稟議書、利用規程、ユースケース申請、リスク評価、月次評価、インシデント記録、ベンダー質問票を置く。

## 相互参照の流れ

- 00を入口とし、01が02・04・05・06を参照して導入判断を行う。
- 01の判断結果を07のパイロット計画へ渡す。
- 08・09は03〜07の統制を前提条件とする。
- 07の実績値を02へ戻し、10の判断ゲートで継続・拡大・中止を決める。
- 統制要件の正本は03・04に集約し、05・08・09で重複定義しない。

## 現状00〜09の過不足

- 01・04・05で「学習利用」「入力可否」が重複している。
- 03・07・09で効果測定とパイロット運営が分散している。
- 04・07でSSO、ログ、コネクタ統制が重複している。
- 05は「ベンダー比較」と「プラン階層比較」が混在しているため、比較軸を固定する必要がある。
- 06は機能比較に偏っており、運用要員、障害対応、TCO、撤退容易性が不足している。
- 08は対象が限定的なため、全体の必須章ではなく独立した導入トラックとして扱う。
- 変更管理、教育、責任分担、証跡運用、調達・契約、失敗時の停止基準が不足している。

# 4. 受入基準・出典要件

## 全記事共通

- 記事冒頭に「対象読者、答える問い、対象範囲、対象外、確認日」を置く。
- 結論ごとに「事実」「本プロジェクトの判断」「自社で確認すべき事項」を分ける。
- 意思決定に重要な主張は、主張・出典・確認日・適用条件を対応付ける。
- 反証、適用できない条件、未知・未確認事項を明記する。
- 記事末尾に具体的な判断結果または実務成果物を置く。
- 可変情報には再確認期限を設定し、四半期更新対象を一覧化する。
- 比較表の空欄は禁止し、「非対応」「不明」「要問い合わせ」「契約依存」を使い分ける。
- 効果の主張はベンダー事例だけで断定せず、原研究・公的調査・第三者研究で補強する。

## 記事別の強化点

- 01：重み付き判断基準、必須条件、除外条件、停止条件を受入対象にする。
- 02：ベースライン、計算式、感度分析、品質悪化・レビュー工数を含める。
- 04：脅威モデル、情報区分表、契約確認質問、インシデント経路を必須にする。
- 05：同一確認日・同一比較軸で調査し、料金と機能を契約単位で区別する。
- 06：構成図、責任分界、必要要員、TCO、撤退手順を必須にする。
- 07：対象業務ごとの事前値・事後値、証跡、利用者フィードバック、停止条件を必須にする。
- 08：権限越境テスト、コネクタ審査、読み取り／書き込み分離、人の承認点を必須にする。
- 09：コードレビュー、テスト、秘密検知、依存関係確認、実行環境分離を必須にする。
- 10：各フェーズの責任者、成果物、期限、Go／Hold／Stop条件を必須にする。

# 6. GitHub Issueの分割方針

## 管理階層

- Milestone：`v1 意思決定パック`、`v1.1 パイロット実務パック`、`四半期更新`。
- エピックIssue：意思決定、ガバナンス、製品選定、パイロット、エージェント、基盤整備。
- 記事Issue：記事全体の問い、構成、統合、最終受入を管理。
- 子Issue：出典収集、比較表、図表、テンプレート、レビュー、更新確認を管理。

## 適切な粒度

- 1 Issueは原則として0.5〜2日程度、1つのレビュー可能な成果物にする。
- 1 PRで複数記事を横断的に書き換えない。
- ベンダー比較は「ベンダー×契約形態」単位で調査し、統合Issueで比較表にまとめる。
- セキュリティは「情報分類」「契約」「ID管理」「ログ」「コネクタ」「インシデント」に分割する。
- 出典の定期確認は執筆Issueと分離し、四半期ごとの更新Issueとして再利用する。

## 最初に起票するエピック

- 基盤規約・受入基準の強化。
- 暫定AI利用規程と責任分担。
- 情シス限定パイロット実施パック。
- 候補プランの統制・契約比較。
- セキュリティ／法務／調達チェックリスト。
- 導入後90日評価と継続判断。
